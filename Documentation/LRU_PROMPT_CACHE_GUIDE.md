# LRU Prompt Cache Implementation Guide

## 1. Purpose

This document explains the in-process Least Recently Used (LRU) cache added to KnowLayer. The cache stores successful LLM responses for repeated prompts so identical requests can be answered without making another OpenRouter or Groq API call.

The implementation is intentionally small and dependency-free. It uses Python's standard library and is integrated at the shared LLM provider boundary.

## 2. What Was Implemented

The implementation has four parts:

1. `PromptLRUCache` stores prompt-response pairs in memory.
2. `FallbackLLMProvider` checks the cache before calling an LLM provider.
3. Successful responses are added to the cache after generation.
4. `LLM_CACHE_SIZE` controls the maximum number of cached responses.

The main files are:

- `app/infrastructure/llm/prompt_cache.py`
- `app/infrastructure/llm/fallback_llm_provider.py`
- `app/core/settings.py`
- `.env.example`
- `tests/unit/test_prompt_cache.py`

## 3. What LRU Means

LRU means Least Recently Used.

If the cache capacity is two entries and it contains prompts A and B:

```text
A, B
```

Reading A makes it the most recently used entry:

```text
B, A
```

Adding prompt C exceeds the capacity, so B is removed:

```text
A, C
```

The cache keeps frequently reused prompts and removes older prompts when it reaches its limit.

## 4. How Responses Are Stored

The cache uses an `OrderedDict`:

```python
self._entries: OrderedDict[str, str] = OrderedDict()
```

Each entry contains:

- Key: a deterministic JSON representation of the chat messages
- Value: the generated response string

Example conceptually:

```text
{
  "[{\"content\":\"How many leave days do I receive?\",\"role\":\"user\"}]":
    "Eligible regular employees receive 18 days of Annual Leave..."
}
```

The actual key is generated by:

```python
json.dumps(
    messages,
    sort_keys=True,
    separators=(",", ":"),
)
```

Sorting keys and using consistent separators ensures equivalent message structures produce the same cache key.

## 5. Request Flow

A normal request follows this path:

```text
User question
  -> Streamlit UI
  -> POST /api/chat
  -> QueryOrchestrator
  -> RetrievalService
  -> selected document context
  -> FallbackLLMProvider.generate(messages)
  -> PromptLRUCache.get(messages)
  -> cache hit: return stored response
  -> cache miss: call OpenRouter
  -> OpenRouter failure: call Groq fallback
  -> cache successful response
  -> return answer and citations
```

The cache is placed in `FallbackLLMProvider` because both the primary and fallback provider calls pass through that class. This avoids duplicating caching logic in `OpenRouterClient` and `GroqClient`.

## 6. Cache Hit Behavior

When a prompt is already cached:

1. `FallbackLLMProvider.generate()` calls `cache.get(messages)`.
2. The cache finds the serialized message key.
3. The entry is moved to the end of the `OrderedDict`.
4. The stored response is returned immediately.
5. No OpenRouter or Groq request is made.

Moving the entry to the end marks it as recently used and preserves LRU ordering.

## 7. Cache Miss Behavior

When a prompt is not cached:

1. The primary OpenRouter provider is called.
2. If it succeeds, the response is stored and returned.
3. If it fails with `LLMProviderError`, the Groq fallback is called.
4. If Groq succeeds, the fallback response is stored and returned.
5. If both providers fail, the error is raised and nothing is cached.

Provider failures are deliberately not cached. A temporary network error, expired key, or provider outage should not prevent a later retry from working.

## 8. Configuration

The default cache size is 128 responses.

Add this setting to `.env` if a different capacity is needed:

```env
LLM_CACHE_SIZE=128
```

Examples:

```env
# Keep up to 500 prompt responses in memory
LLM_CACHE_SIZE=500
```

```env
# Disable caching
LLM_CACHE_SIZE=0
```

The setting is read in `app/core/settings.py`:

```python
LLM_CACHE_SIZE = int(os.getenv("LLM_CACHE_SIZE", "128"))
```

A value of zero disables storage and lookup. Negative values are normalized to zero by `PromptLRUCache`.

After changing `.env`, restart the API process. Environment values are loaded when the Python process starts.

## 11. What the Tests Cover

`tests/unit/test_prompt_cache.py` verifies:

- A repeated prompt returns the cached response.
- The underlying provider is called only once for a repeated prompt.
- The least-recently-used entry is evicted when capacity is exceeded.

## 12. Demonstrating LRU Eviction to the Team

The simplest demonstration is:

```python
from app.infrastructure.llm.prompt_cache import PromptLRUCache

cache = PromptLRUCache(maxsize=2)

first = [{"role": "user", "content": "first"}]
second = [{"role": "user", "content": "second"}]
third = [{"role": "user", "content": "third"}]

cache.put(first, "response one")
cache.put(second, "response two")

# Reading first makes it recently used.
cache.get(first)

# The cache is full, so second is evicted.
cache.put(third, "response three")

assert cache.get(first) == "response one"
assert cache.get(second) is None
assert cache.get(third) == "response three"
```

The important point is that reading an entry changes its position in the LRU order.

## 13. Demonstrating Provider-Level Caching

Ask the same question twice through Streamlit. The first request performs retrieval and generation. The second identical request can reuse the cached generated answer, provided the process has not restarted and the cache has not evicted the entry.

Caching applies to the final LLM message list. If the selected document context, system instructions, or user question changes, the serialized messages change and the request is treated as a cache miss.

## 15. Important Limitations

### Process-local storage

The cache exists only in the memory of one API process. It is not shared between processes, machines, or workers.

### Restart clears the cache

Stopping or restarting FastAPI removes all cached responses.

### No disk persistence

The cache does not write prompt content or generated responses to `.chroma`, SQLite, or a file.

### No cross-worker sharing

If Uvicorn runs multiple workers, each worker has its own cache. A request may miss the cache depending on which worker receives it.

### Memory usage

Each entry contains the full serialized prompt key and response string. Increasing `LLM_CACHE_SIZE` increases memory usage.

### Sensitive content

Prompt and response content remains in process memory while cached. Do not cache sensitive prompts if the application threat model does not permit them. Set `LLM_CACHE_SIZE=0` to disable caching.

### Exact-message matching

The cache is exact-match based. Semantically similar questions with different wording do not share a cache entry.

## 16. Thread Safety

`PromptLRUCache` uses `RLock` around reads, writes, ordering updates, and clearing. This protects the `OrderedDict` when multiple request threads access the same provider instance.

The lock protects cache structure only. It does not serialize the actual LLM network calls.

## 17. Cache Invalidation

The current implementation provides `clear()` for explicit invalidation:

```python
provider.cache.clear()
```

A future admin endpoint or lifecycle hook could expose this operation if required. Currently, restarting the API is the simplest way to clear all entries.

## 18. Why the `llm-caching` Package Was Not Used Directly

The linked `llm-caching` PyPI package provides a general caching wrapper and proxy with SQLite or Redis storage. The application's requested behavior is a small, bounded, process-local LRU cache for the existing provider interface.

Using a local implementation keeps the behavior explicit:

- no Redis server is required;
- no proxy process is required;
- no additional runtime service is introduced;
- the cache capacity and eviction behavior are directly testable;
- the existing provider and fallback interfaces remain unchanged.

A Redis-backed implementation would be appropriate later if multiple API workers or multiple application instances need to share cached responses.

## 19. Production Considerations

For a single-process local deployment, the current implementation is sufficient.

For a multi-worker or distributed deployment, consider:

- Redis or another shared cache;
- a namespace containing provider and model identifiers;
- time-based expiration in addition to LRU eviction;
- explicit invalidation when prompts or system instructions change;
- metrics for cache hits, misses, evictions, and errors;
- response redaction or exclusion rules for sensitive data;
- a maximum prompt and response size.

A shared cache should also include the model name, provider name, system prompt version, retrieval configuration, and any other input that changes the generated answer.

## 20. Troubleshooting

### Repeated requests still call the provider

Check:

1. `LLM_CACHE_SIZE` is not `0`.
2. The API was restarted after changing `.env`.
3. The requests contain exactly the same messages.
4. The cache capacity was not exceeded.
5. Multiple API workers are not routing requests to different processes.

### Cached answers appear stale

Restart the API or call:

```python
provider.cache.clear()
```

Then retry the question.

### The API returns provider errors

Caching does not replace provider credentials or provider availability. Check the OpenRouter and Groq configuration separately. Failed responses are intentionally not cached, so correcting the configuration allows the next request to retry.

### Memory usage is too high

Lower the setting:

```env
LLM_CACHE_SIZE=32
```

Or disable caching:

```env
LLM_CACHE_SIZE=0
```

## 21. Summary

The implementation adds a bounded, thread-safe, exact-match LRU cache around successful LLM responses. It improves repeated-prompt latency and reduces duplicate provider calls while preserving the existing OpenRouter-first and Groq-fallback behavior.

The cache is:

- in memory;
- process local;
- cleared on restart;
- configurable through `LLM_CACHE_SIZE`;
- disabled with `LLM_CACHE_SIZE=0`;
- tested for hits, eviction, disabled mode, and failure handling.

## 22. Storing Generated Answers as FAQs

Grounded answers can also be stored as FAQ documents in MongoDB. FAQ persistence is optional. When `MONGODB_URI` is empty, the application continues to run without a MongoDB connection.

The FAQ store is called after:

1. Retrieval finds relevant document evidence.
2. The LLM generates an answer.
3. Citations are assembled from the same selected evidence.

This means only answers with supporting evidence are persisted. Empty-retrieval responses are not stored.

### MongoDB configuration

Add these values to the local `.env` file:

```env
MONGODB_URI=mongodb://localhost:27017
FAQ_DATABASE_NAME=knowlayer
FAQ_COLLECTION_NAME=faqs
MONGODB_SERVER_SELECTION_TIMEOUT_MS=2000
```

For MongoDB Atlas, use the connection string supplied by Atlas:

```env
MONGODB_URI=mongodb+srv://<username>:<password>@<cluster>/<database>
```

Do not commit `.env` or place real credentials in `.env.example`.

Install the dependency with:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

The application uses the `pymongo` driver.

### FAQ document shape

Each FAQ is stored in the configured collection in this form:

```json
{
  "question": "How many Annual Leave days do I receive?",
  "question_key": "how many annual leave days do i receive?",
  "answer": "Eligible regular employees receive 18 days of Annual Leave per calendar year.",
  "citations": [
    {
      "source": "NEXORA TECHNOLOGIES PVT.docx",
      "section": "Policy",
      "text": "Eligible regular employees receive 18 days..."
    }
  ],
  "created_at": "UTC datetime",
  "updated_at": "UTC datetime"
}
```

### FAQ deduplication

`question_key` is created by trimming whitespace, collapsing repeated whitespace, and converting the question to lowercase. MongoDB creates a unique index on this field.

The store uses an upsert:

```text
same normalized question -> update existing FAQ
new normalized question  -> insert new FAQ
```

As a result, repeated versions of the same question do not create duplicate FAQ documents.

### MongoDB failure behavior

FAQ persistence is deliberately best effort. If MongoDB is unavailable or an insert/update fails:

- the failure is logged;
- the generated chat response is still returned to the user;
- the request is not converted into a 500 error because of FAQ storage.

This keeps MongoDB from becoming a hard dependency for answering questions.
